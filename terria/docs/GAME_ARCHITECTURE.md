# TERRIA — game architecture (server + client contract)

The map layer (everything under `src/world`, `src/rendering`, `src/camera`)
stays as it is. The game is three new parts:

```
src/game/      PURE shared rules (client + server): config, rules, market, types, bits
src/app/       client game UI on top of the map (HUD, panels, city layer, API client)
server/        Cloudflare Worker (API + Telegram webhook + cron), D1 schema
public/regions generated by `npm run regions` (tools/build-regions.ts), 1001 JSON files
```

## Ownership model

* 1000 regions = 1000 players. A player gets one whole region; at the start
  1 % of it is unlocked (the starter plot, ~9x9 cells of 16 m) with a 4x4
  town hall in its north-west corner. The rest of the region is bought cell by
  cell (`land` action), always connected to the city. Nobody else can buy
  inside your region.
* Region masks (`/regions/<id>.json`, `RegionMaskDTO`) say which cells of the
  region are buildable and wooded. Static assets: free on Cloudflare, read by
  the client with `fetch` and by the Worker with `env.ASSETS.fetch`.
* Balance thresholds (town hall population) scale with `regionScale = cells / 8500`.

## Economy

`src/game/rules.ts` is the single source of truth:
`advance(city, now, mask)` integrates production lazily (no timers on the
server, offline production capped at 12 h, the city never dies),
`applyAction(city, action, mask, now)` validates and applies one action.
The client runs the same functions to predict the result before the server
answers.

## Server (Cloudflare Worker, free plan)

Bindings: `DB` (D1 `terria`), `ASSETS` (built client + region masks),
secrets `BOT_TOKEN` (set by the owner in the dashboard), `WEBHOOK_SECRET`
(random, set at deploy), vars `PUBLIC_URL`, `BOT_USERNAME`, `DEV_AUTH` ("1"
only for local dev).

Assets are served without invoking the Worker (`run_worker_first: ["/api/*", "/tg/*"]`),
so page loads are free and unlimited; only API calls count against the
100 000 requests/day.

### Auth

Every `/api/*` request carries `Authorization: tma <initData>` (raw
`Telegram.WebApp.initData`). The Worker checks the HMAC with `BOT_TOKEN`
(`secret = HMAC_SHA256("WebAppData", bot_token)`, `hash = HMAC_SHA256(secret, data_check_string)`),
rejects `auth_date` older than 24 h, and takes `user.id`, `user.first_name`,
`user.username`. With `DEV_AUTH=1` the header `Authorization: dev <id>` is accepted.

### D1 schema (server/schema.sql)

```
users(id INTEGER PK, name TEXT, username TEXT, region_id INTEGER NULL, crystals INTEGER NOT NULL DEFAULT 0 CHECK(crystals >= 0),
      created_at INTEGER, last_seen INTEGER, bot_chat INTEGER DEFAULT 0, warned_at INTEGER DEFAULT 0)
cities(region_id INTEGER PK, user_id INTEGER UNIQUE, name TEXT, th INTEGER, pop INTEGER, status TEXT,   -- 'active' | 'abandoned'
       coins REAL CHECK(coins >= 0), wood REAL CHECK(wood >= 0), stone REAL CHECK(...), iron REAL ..., food REAL ..., goods REAL ...,
       data TEXT,      -- CityState JSON without res/crystals (those live in columns)
       ver INTEGER, last_seen INTEGER, created_at INTEGER)
orders(id INTEGER PK AUTOINCREMENT, region_id INTEGER, side TEXT, res TEXT, qty INTEGER, remaining INTEGER CHECK(remaining >= 0),
       total REAL, escrow REAL CHECK(escrow >= 0), status TEXT, created_at INTEGER, expires_at INTEGER)
       INDEX(res, side, status), INDEX(region_id, status), INDEX(status, expires_at)
trades(id INTEGER PK AUTOINCREMENT, res TEXT, qty INTEGER, unit REAL, at INTEGER, kind TEXT, seller INTEGER, buyer INTEGER)
prices(res TEXT PK, ref REAL)
payments(charge_id TEXT PK, user_id INTEGER, pack TEXT, stars INTEGER, crystals INTEGER, at INTEGER, refunded INTEGER DEFAULT 0)
meta(key TEXT PK, value TEXT)
guard(x INTEGER NOT NULL)   -- optimistic-lock trick, see below
```

Crystals live in `users` (they survive losing an abandoned city).
`CityState.crystals` is filled from `users.crystals` when sent to the client.

**Atomicity without transactions.** A D1 `batch()` is one transaction: if any
statement fails, everything rolls back. Two tricks make a failed condition
fail the statement:
* `CHECK(x >= 0)` on every balance column: spending more than you have aborts.
* version guard: `INSERT INTO guard(x) SELECT NULL WHERE (SELECT ver FROM cities WHERE region_id=?1) != ?2`
  inserts NULL into a NOT NULL column when someone else changed the city in
  between, which aborts the batch; the Worker re-reads and retries (3 times).

Balance changes are written as deltas (`SET wood = wood + ?`) so that a trade
filled by another player at the same moment is never lost.

**Idempotency.** Every mutating request carries `op` (client UUID). The last
32 op ids live in `CityState.ops`; a repeated op returns the current state
without applying anything.

### Endpoints

| Method | Path | Body | Returns |
|---|---|---|---|
| GET | /api/me | – | `MeResponse` (advances the city lazily; persists only if > 1 h passed) |
| POST | /api/city | `{ name }` | `MeResponse` — assigns a random free region (or recycles the oldest abandoned one), creates the city |
| POST | /api/city/actions | `{ op, actions: Action[] }` | `CityResponse` with per-action `results` |
| GET | /api/world | – | `{ cities: WorldCitySummary[] }`, edge-cached 60 s |
| GET | /api/city/:regionId | – | `PublicCity`, edge-cached 60 s |
| GET | /api/market | – | `MarketResponse` (prices, today's system quota, my orders) |
| GET | /api/market/orders?res=wood&side=buy | – | `{ orders: Order[] }` best price first, open only, 50 max |
| GET | /api/market/trades?res=wood | – | `{ trades: Trade[] }` last 30 |
| POST | /api/market/system | `{ op, side: 'buy'\|'sell', res, qty }` | `CityResponse` — buy from / sell to the system at the live price |
| POST | /api/market/orders | `{ op, side, res, qty, total }` | `CityResponse & { order }` — escrows coins (buy) or goods (sell) |
| POST | /api/market/orders/:id/fill | `{ op, qty }` | `CityResponse` — partial fills allowed |
| POST | /api/market/orders/:id/cancel | `{ op }` | `CityResponse` — escrow returned |
| GET | /api/shop | – | `{ packs: CrystalPack[], crystals }` |
| POST | /api/shop/invoice | `{ pack }` | `{ link }` from `createInvoiceLink` (currency XTR) |
| POST | /tg/webhook | Telegram update | handles /start, pre_checkout_query, successful_payment, refunded_payment |

Errors: HTTP 4xx with `ApiError { error, message }` (`error` keys of `ERRORS` in rules.ts plus
`unauthorized`, `no_city`, `full`, `conflict`, `exchange_locked`, `own_order`, `expired`, `bad_request`).

### Market rules

* **System market ("по рыночной цене")**: always available. The player buys
  at `ref * 1.25` and sells at `ref * 0.75`, selling is limited to
  `300 * townhall` units per resource per day (prevents printing coins).
  Every system deal nudges `ref` a little (supply / demand).
* **Exchange (online, between players)**: opens at town hall 2. Any price
  ("куплю 5000 древесины за 1 монету" is valid). The creator's coins (buy) or
  goods (sell) go to escrow. Anyone who has the goods / coins fills it fully
  or partly. Seller pays a 2 % fee (burned). Orders expire after 72 h; cron
  returns the escrow. Max 10 open orders per city. Exchange trades move `ref`
  with a weight that grows with volume and is clamped (0.4x … 2.5x base), so a
  single silly price cannot crash the market.

### Inactive cities

* `untouched` (no action ever) → abandoned after 3 days;
  town hall 1–2 → 7 days, 3–4 → 21 days, 5–6 → 45 days without a visit.
* 2 days before, the bot sends a reminder (if the user ever started the bot).
* Abandoned cities stay on the map (greyed, "заброшен"). If the owner comes
  back, the city is active again with everything in place.
* An abandoned region is only recycled when a new player arrives and no free
  region is left (oldest first). Then the old city is deleted; the user keeps
  crystals and payments and can start again in a free region.
* If nothing can be recycled, `POST /api/city` answers `full` (waiting list).

### Payments (Telegram Stars)

`createInvoiceLink` with `currency: "XTR"`, empty `provider_token`, payload
`<userId>:<packId>:<nonce>`. The client opens it with `Telegram.WebApp.openInvoice`.
`pre_checkout_query` is answered `ok` only for known packs and existing users.
`successful_payment` inserts into `payments` (PK `telegram_payment_charge_id`,
so a repeated update cannot credit twice) and adds crystals in the same batch.
`refunded_payment` marks it refunded and removes the crystals (down to 0).

### Bot setup

On the first cron run after `BOT_TOKEN` appears (and whenever `BOT_SETUP_VERSION`
changes) the Worker calls `setWebhook` (with `secret_token`), `setMyCommands`,
`setMyDescription`, `setMyShortDescription`, `setChatMenuButton` (web_app →
PUBLIC_URL) and stores the version in `meta`. `/start` answers with a welcome
text and an inline web_app button «Играть».

### Cron (one trigger, every 30 min)

Expire orders, mark inactive cities, send reminders, bot setup check,
recompute `/api/world` summary cache.
